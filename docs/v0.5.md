# V0.5 performance reconstruction

Version:0.5.0-experimental; Android version code5. Baseline:v0.4.0-candidate.1, sourceca330131115ee983a6457efa33ff513ac34803ad, exact released browser SHA256f1f6a9e9b19c0bc8210b5bab4ef91e9b03c854f0b895cda0c965ae6779a45aad.

## Implemented changes

- `src/terrain/london.js`: one runtime streaming entry, cached cell coordinates, unique landmark material updates, identical detailed-LOD reuse and asynchronous prepared-tile integration. Original distance selection, tile granularity, collision data and shadow flags remain in use.
- `scripts/build-london-geometry.mjs` and `src/terrain/prepared-geometry.js`: generate exact final Float32 attributes offline, gzip each tile independently, verify generator/input/output hashes, lazily decode one tile at a time, wrap shared attribute views without extra copies, and retain complete visible meshes until replacements finish. Cancellation/reset rejects stale work; unsupported decompression/corruption uses the existing runtime generator.
- `src/simulator.js`: remove duplicate London dispatch, retain active elapsed-time physics debt, bound catch-up to120 fixed120Hz steps per frame and reset clocks immediately at pause/help/replay transitions. Weather and traffic state follow executed physics time. Camera/effect interpolation keeps its stability clamp; diagnostics expose debt.
- `src/rendering/london-lighting.js`: remove scene-wide material invalidation on shadow toggles. r128 already tracks light/shadow program variants. Existing shadow map resolution, coverage and cadence remain.
- `src/terrain/imagery.js`: compute selection distances once, avoid sorting unchanged positions, index entries byID and count loads/reloads/evictions/stale decodes. Same texture residency ceiling, concurrency and selection ordering.
- `src/rendering/diagnostics.js`: opt-in bounded CPU-phase observations. CPU render submission is never labelled GPU execution.

These are CategoryA changes to scene geometry/rendering intent. The simulation clock fix intentionally corrects elapsed-time behaviour; it is not a visual-quality tradeoff. No resolution/profile/density/texture/shadow reduction was introduced.

## Local evidence at source preparation

All161 unit tests passed, plus configuration10/10, Android metadata29/29 and delivery guards13/13. The full prepared pack contains866 variants across433 cells. Every4,330 attribute array and233,337,888 bytes matches the original eight-building runtime batches exactly; merged culling bounds also match. See`benchmarks/london-v0.5/prepared-equivalence.json`.

Three alternating-order CPU-only streaming rounds eliminate7,588 runtime geometry-generation calls per route. Across initial construction and movement/revisit phases, median total synchronous-update work fell49.2–73.1% and convergence wall time fell29.7–66.6%. Total process CPU includes native decompression and is mixed: one return phase increased7.3%. This fast event-loop experiment excludes GPU rendering and is not an FPS or A51 speedup claim. Raw paired observations and caveats are in`cpu-paired.json`.

A clock regression fixture verifies ten active wall seconds produce ten simulated seconds at60,30,10 and2FPS once retained debt drains. The prior implementation produced approximately five seconds at10FPS and one second at2FPS. The120Hz physics integrator itself is unchanged.

An initial local render-harness smoke run was rejected: it waited for building convergence but could capture unfinished local road queues. Faster prepared construction exposed this invalid warm-up assumption (London skyline road tiles12 versus6). Its short timings are not performance evidence. The corrected harness derives the required road-cell count from the immutable road input and waits for it; matched captures and packaging also require equal geometry bytes, tile counts and submitted primitive counts. The rejected partial report is retained in`benchmarks/london-v0.5/rejected/paired-smoke-incomplete-road-warm.json`.

## Costs and rejected alternatives

Prepared assets cost about30.5MB compressed and increase the self-contained HTML from46.8MB to88.1MB. All decoded variants would occupy222.5MiB before GPU copies; eager decoding was rejected. The decoder retains no decoded cache and permits one active stream. Device/browser peak heap and APK/WebView startup must be checked in the delivery evidence.

No engine migration, worker framework, quantization, texture compression, shadow disablement, broader geometry approximation or reduced rendering resolution was introduced. The fallback generator retains its inherited soft budget and can still stall on an unusually complex polygon when native decompression is unavailable.

## Reproduction and delivery gates

1. Download`Lightning-London-Scenery.zip` and`Lightning-F35B-Web.zip` from the immutablev0.4.0-candidate.1 release into`.tmp/v04-assets`.
2. Run`python3 scripts/restore-v04-scenery.py .tmp/v04-assets --browser` (archive and every output hash checked).
3. Run`node scripts/build-london-geometry.mjs`, then`npm test` and`npm run build`.
4. With full Git history, run`node scripts/verify-london-geometry.mjs` and`node scripts/benchmark-london-paired-v05.mjs`. Their default baseline is the exact published source.
5. Install the locked Playwright Chromium and Python requirements, then run the existing browser/London/offline/lifecycle checks. Run`node scripts/verify-v05.mjs dist/v04-baseline.html dist/index.html` and`python scripts/compare-v05.py`.
6. Run`LONDON_ENDURANCE_SECONDS=1200 node scripts/endurance-london.mjs dist/index.html`.
7. Build with`bash scripts/build-android.sh`; run genuineAPI33 emulator instrumentation using`android/run-instrumentation.sh`. Combine jobs with`package-v05.py` only after all gates pass.

The dedicated workflow records exact source/build hashes, browser/WebView identities, controlled repeated rendering observations, nineteen matched visual fixtures and differences, actual-loop CPU phases, offline checks, Android installation XML and sustained-flight evidence. Remote execution results are generated by that workflow; this document does not predeclare their success.

Physical Galaxy A51/MaliGPU frame rate, touch/gyro feel, thermal throttling, battery and long-duration phone stability are NOT TESTED without a connected device. Cloud SwiftShader measurements cannot establish the30FPS target. Active before/after trajectories differ because simulation time is corrected; only matched fixed scenes support controlled rendering comparisons.
